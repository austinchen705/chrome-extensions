# 狀態觸發

- 規則判斷在 `catworld-auto-command/trigger-engine.js`（不碰 DOM，讀數、時間、送出指令都由呼叫端傳入），content script 與 popup 共用；規則狀態機與安全上限的語意寫在該檔開頭註解。manifest 的 content script 與 popup 的備援注入都要帶上它。
- **安全機制的「角色狀態」（`allowedStatuses`；設定頁沒有總開關了，引擎的 `requireNormal` 只剩舊設定與測試用）**：角色狀態（遊戲的 `#status` 文字，`content.js` 的 `readStatus`，讀不到＝null）要在該組的 `allowedStatuses` 裡才觸發（`trigger-engine.js` 的 `statusBlock`，`runPending`、`onText`、`tick` 三處共用；原因文字寫進規則的 `note`，例如「角色狀態「中毒」不在允許的狀態裡，暫不觸發」）。比對前先拿掉狀態文字結尾的「:數字」（遊戲寫「包紮:27」），只比名稱。`cleanStatuses` 整理清單：**「正常」一定在最前面、不能拿掉**，其餘去空白、去重、每個最多 `MAX_STATUS_LENGTH`（20）字、最多 `MAX_STATUSES`（20）個、非文字丟掉；沒有這個欄位（新設定、舊的儲存，或不是陣列）＝「正常」加上 `STATUS_PRESETS` 全部（`normalizeConfig` 預設，設定頁沒存過清單時也顯示全勾）；存過的清單（包含只有「正常」的空清單）照清單。內建選項 `STATUS_PRESETS`＝忙碌、中毒、酒醉、包紮（使用者告知的已知狀態，**我沒查到遊戲完整的狀態清單**，`#status` 是伺服器傳來的文字），其他狀態由設定頁的欄位自己填（用 `、` `,` `，` 或換行分開）。設定頁每組有一份（`#statuses-<組>` 裡的 `input[data-status]` 與 `#statusCustom-<組>`），存進 `allowedStatuses` 陣列（內建選項勾的在前、自己填的在後），**不再寫 `requireNormal`**（引擎預設 `requireNormal !== false`＝一律檢查，所以只有「有勾才允許」）。舊設定 `requireNormal: false` 且沒有 `allowedStatuses` 的，設定頁顯示時把內建選項都勾起來（`legacyOff`），下次存檔才寫進去；沒開過設定頁、也沒存過之前，引擎仍照舊設定的 `requireNormal: false` 不檢查。引擎的 `io.status()` 優先；只給舊的 `io.isNormal()` 時照舊只認「正常」。測試在 `tests/integration/game/trigger-status.test.js`（底座的頁面沒有 `#status`，要用的測試自己放一個）。
- 看門狗、送出佇列、關鍵字在「定時或觸發任一個在跑」時都要作用（`active()`），驗證碼偵測與自動辨識則閒置時也作用（手動 `reward` 領獎也要幫忙輸入），新增會送指令的功能要接同一套；只有輸出區 `#content` 裡的變動算遊戲輸出（`inContent`），右上角每秒跳的時鐘 `#uptime`、`#monitor`、地圖、巨集、設定視窗、重連倒數 `#notice` 都不算，時鐘每秒一跳、漏掉它看門狗永遠不會響。
- **聊天指令與其他指令之間的切換間隔**（`content.js` 的 `pumpQueue`）：聊天指令（自動回覆 `reply`、劇本 `tell`，佇列項目的來源或巨集 owner 是 `chat`／`script`，`isChatEntry`）和其他來源的指令（觸發、定時、隨機、巡怪、使用者的巨集）前後相接時，`pumpQueue` 在送出前另外抽一段 `SWITCH_GAP_MS`（1.5～4 秒，每次排程抽一次），和共用的「指令間隔」、巡怪間隔取較大的：比較「上一個從佇列送出的是不是聊天」（`lastSentChat`）與下一個項目，不同才加；聊天接聊天（劇本同一輪的幾則）、其他接其他維持原本的間隔。上限一定要小於 `NO_REPLY_MS`（8 秒），不開放設定；不走佇列的 `sc`、`reward`、驗證碼答案不更新 `lastSentChat`。間隔是從 `lastSentAt` 算起，所以第一次送出本來就不會等。測試 `tests/integration/game/chat-send-gap.test.js`（量真實時間，頁面計時器縮小 10 倍，間隔約 150～400 毫秒；含劇本 `tell`、定時與隨機指令、觸發巨集 `@等待`、最優先巨集、先進先出、停止關鍵字與真人驗證出現時等待中的聊天指令不再送出；巡怪的那條在 `tests/integration/game/map-hunt-core.test.js` 的 `chat:`）。**閒置（idle）暫停本來就不取消佇列裡的指令**，所以不算在「停止」路徑裡；`sc`、`reward`、驗證碼答案不走佇列、沒有改動，沒有單獨的測試。
- 觸發分成「戰鬥」「練功」兩組（`trigger-engine.js` 的 `GROUPS`），功能相同、完全獨立：各自的設定存在 `triggerGroupSettings.<id>`、各自一個引擎與計時器，送出佇列來源是 `trigger:<id>`。`START_TRIGGER` / `STOP_TRIGGER` / `REARM_RULE` 一定要帶 `group`（未知或沒帶回 `ok:false`）；`STATUS` 回 `stats`（讀數，共用）與 `triggerGroups.<id>`。popup 用 `<template id="triggerPaneTemplate">` 為每組產生一個分頁，template 內的 id 都帶 `-__G__`；新增一組只要加進 `GROUPS`。舊的 `triggerSettings` 由 `loadGroupSettings` 整份放進練功組。驗證碼、`stopEverything` 對所有組一起作用。規則的 `stopGroup`（規則卡片裡的「命中送出後停止○○觸發」，數值與關鍵字規則都有）在 `content.js` 的 `send` 回呼處理：**先** `stopTriggers` 再把這次的指令用 `startMacro(commands.join(';'), 'trigger:<id>')` 送出（順序反過來指令會被 `stopTriggers` 的 `dropQueue` 丟掉；用巨集送是因為巨集執行中算 `active()`，定時與另一組都沒在跑時最後一個指令才送得出去；同一輪好幾條規則一起送出時只在 `group.on` 還是 true 時停一次，再停會把前一條剛啟動的巨集取消掉；停了之後同一輪才送出的其他規則也走巨集）；引擎的 `io.send(commands, index)` 帶規則索引，停止原因才寫得出是哪條規則；勾了 `stopGroup` 的規則指令可以留空（`normalizeRule` 以「有指令或有勾停止」判斷規則有效，`send` 沒指令就不起巨集），沒勾的指令留空仍是未啟用。測試在 `tests/integration/game/trigger-stop-after-fire.test.js`。
- 規則的 `number`（最後一個指令後面加隨機數字，`{ min, max }`）：`trigger-engine.js` 的 `cleanNumber`（0～`NUMBER_LIMIT` 的數字，寫反交換，其他丟掉）在 `normalizeRule` 保留，`withNumber(commands, number)` 在 `content.js` 的 `send` 回呼一開始就套用（每次命中重抽，只動最後一個指令，所以 `stopGroup`、`priority` 兩條路徑都帶得到）；設定頁的勾選與範圍欄在 `popup.js` 的 `numberFields`（欄位空白退回 50～150），**只在練功組的卡片放，戰鬥組與定時分頁都沒有**（引擎與 `send` 不分組，儲存裡有 `number` 的規則照樣會加）。測試在 `tests/integration/game/trigger-number.test.js`。
- 規則指令欄的 `@巨集 N`（N 是遊戲巨集視窗的列號 1～90，兩組、數值與關鍵字所有規則都可以寫）：`macro-io.js` 的 `macroRef`（認這個寫法，只認 `@巨集` 加整數）、`containsMacroRef`（一個指令裡有沒有，**整個指令或 `;` 之間的某一段都算**，`edf;@巨集 18` 要認得，只比對整串會讓它原樣送給遊戲而得到「什麼﹖」）與 `expandMacroRefs(commands, raw)`（純函式，raw 是 `localStorage.MACROS` 原文，沒有參照時完全不讀它；有參照的指令逐段處理，解不開的段落只丟那一段，一段都不剩才丟整個指令，沒有參照的指令原樣不動）把它換成那一格的指令文字；`content.js` 在 `send` 回呼一開始呼叫（`readGameMacros` 讀原文），所以**命中當下才讀、改了巨集下一次就用新的**，**格子文字裡空的段落（結尾的 `;`、`;;`）在 `expandMacroRefs` 丟掉**（`parseSteps` 會把它們當成空白指令、`sendCommand` 會送出空白行，遊戲沒有回應時 8 秒看門狗可能誤判成需要驗證；要送 Enter 寫 `<enter>`），丟完什麼都不剩視為「沒有指令」。**隨機數字（`withNumber`）只在規則的最後一個指令不是 `@巨集` 時才套**（`lastIsRef`；套在整格巨集的結尾會讓 `attack;@等待 2` 變成 `@等待 2 87` 而整個被拒絕）。遊戲存的是 `[按鍵值字串, 指令字串]`，第 N 列＝陣列第 N-1 項（`save_custom_macro` 照列順序存，沒按鍵但有指令的列也存），按鍵不影響，只看指令是否為空。讀不到（空、列號超出、沒存過、資料壞、那一格的文字 `CatworldMacro.parseSteps` 解析不了＝`expandMacroRefs` 的 `validate`，`content.js` 的 `macroProblem`）的參照拿掉，原因放進 `macroNote`（命中當下面板「巨集」列紅字 8 秒），其他指令照送、規則不停用；`expandMacroRefs` 回 `used`（成功換進去的格子數），`used > 0` 才改走整條接成巨集的路徑；另外 `triggerSummary` 每秒呼叫 `macroWarnings(group)`（只看啟用中、有 `@巨集` 的規則，沒有任何 `@巨集` 時完全不讀 localStorage）：讀不到就把「⚠ 規則「…」…」放在觸發列最前面、紅字、一直顯示、巨集修好就消失，`STATUS` 的 `triggerGroups.<組>.warning` 帶同一段文字。格子裡再寫 `@巨集 N` 不展開。**有參照的規則整條接成一個巨集（`startMacro(commands.join(';'))`）依序送**，不是一個指令一個指令排：否則格子裡的 `@等待` 會讓後面的指令搶在前面送出（`priority`、`stopGroup` 的路徑本來就是整條接成巨集）；全部參照都解不開、指令是空的就不啟動。測試在 `tests/integration/game/trigger-macro-ref.test.js`（底座的頁面沒有 `localStorage`，用 `preload` 放記憶體版；規則的冷卻用真實時鐘，不受計時器縮小影響；送出後要模擬遊戲回應，否則看門狗會停掉整組）。
- 規則的 `priority`（最優先）由 `content.js` 處理：命中時指令用 `startMacro(…, { priority: true })` 包成 priority 巨集；`currentPriority`（最早的那個）放行，`nextQueued` 只送它的佇列項目，`syncHold` 把其他巨集的 `@等待` 凍結（`frozen`、`remaining`）、放行後接著算；`finishMacroIfDone` 要看 `frozen`，否則被凍結的巨集會被誤判結束。測試在 `tests/integration/game/trigger-priority.test.js`。
- 關鍵字規則（`kind: 'keyword'`）的新文字由 `captchaObserver` 在驗證碼檢查之後交給 `engine.onText`，只取 `#content` 內新增的內容。防迴圈靠「只看新文字、冷卻中的直接丟掉、`>` 開頭的回聲行略過」三件事，改動時不能拿掉任何一個，對應測試（`tests/unit/trigger-keyword.test.js`）要保留。輸出分批到、關鍵字也可以有好幾行（設定頁的欄位是 `<textarea>`，`<input>` 會吃掉貼上的換行），所以 `onText` 不是只比對這一批：引擎留最近 `KEYWORD_WINDOW_MS`（5 秒）的每批文字（`recent`，帶遞增的 `seq`，已壓掉空白、已濾掉回聲行），每條規則自己的 `consumed` 記它用到哪一批，只拿 `consumed` 之後的接起來比對；沒命中不推進（留給下一批），命中或這條規則不是待命（冷卻中、停用）時推進到最新，所以冷卻期間來的文字不會在冷卻結束後補送、同一段文字也不會再觸發第二次。
