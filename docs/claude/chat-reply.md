# 聊天回覆

- 規格與票在 `.scratch/chat-reply/`（不進 git）。`chat-reply.js`（純函式，manifest 與 popup 備援注入都要載入，在 `content.js` 之前）：`parseLine` 認三種私聊行——來訊 `[P]暱稱回答你：內容`、我的回覆 `[P]你告訴暱稱：…`（tell）與 `[P]你回答暱稱：…`（reply）；`>` 開頭的回聲與公開 `[P]你說道：` 不算。`createRecorder` 只處理已收到換行的完整行（輸出分批到、行會被切開），沒有換行的最後一行留到下一批（行被切開時不會記下半句）；每個暱稱記最後一句來訊（配對的鍵是 `personKey`，拿掉暱稱結尾的 `(ID)`：來訊是「暱稱(id)告訴你」、我的回覆行只有暱稱），`PAIR_WINDOW_MS`（2 分鐘）內我回同一個暱稱就配成 `{ said, reply, at }`，回覆含分號或 `@等待` 的不收（會被當巨集；不安全的回覆不會吃掉待配對的來訊，之後乾淨的回覆仍配得上；空的來訊會清掉這個人之前那句）。回覆是打指令時的單行文字，不另外處理換行。`addPair` 同一組 said+reply 不重複、只留最新 `MAX_PAIRS`（500）筆。
- 資料管理（設定頁同一區塊）：`exportText`／`parseImport`／`mergeImported` 是純函式（在 `chat-reply.js`）。格式一行一筆「說 Tab 回」、舊的在前；`parseImport` 整份通過才回 `{ ok: true, pairs }`（兩段都和 `exportText` 一樣把連續空白壓成一個，往返才一致），否則回說明第幾行的 `error`，設定頁不通過就什麼都不寫；`mergeImported` 把匯入的接在後面當最新（`at` 從匯入時刻遞增）、重複的組略過、超過 `MAX_PAIRS` 丟最舊，`dropped` 是被擠掉的原本資料、`trimmed` 是匯入的比上限還多而沒收的（`added` 不含它），兩者分開回報。設定頁的刪除、匯入、清除是讀改寫 `chatPairs`，沒有和遊戲頁的寫入佇列協調：兩次動作之間遊戲頁剛好記了一筆，那筆可能被蓋掉、剛刪的也可能復活（Chrome 儲存沒有原子的讀改寫，視窗很小），這是已知限制。清單新的在前，刪單筆以 said＋reply 比對（不用索引，清單可能剛被遊戲頁更新），清除前 `confirm`；popup 監聽 `storage.onChanged` 重畫，所以遊戲頁新記的會即時出現。
- 設定頁「聊天回覆」區塊（`sec-chat`，欄位 `chatReplyOn`／`chatThreshold`／`chatCooldown`／`chatPerHour`，popup.html 要載入 `chat-reply.js`）每次 `change` 把四欄位交給 `normalizeSettings` 存成一個 `chatReply` 物件並把正規化後的值寫回欄位；測試在 `tests/integration/settings/chat-reply-settings-ui.test.js`。
- 自動回覆：設定 `chrome.storage.local.chatReply`＝`{ enabled, threshold, cooldownSec, perHour, delayMin, delayMax }`（`normalizeSettings`：預設關、只有 `true` 才開、門檻預設 0.5 限制在 0.1～1），`content.js` 啟動時讀、`storage.onChanged` 即時生效。`createRecorder` 的 `onIncoming` 每收到一句非空的來訊就呼叫 `answerChat`：`worthAnswering`（至少兩個字、不是 `>` 回聲）→ `bestReply`（`similarity`＝去標點空白後相鄰兩字的 Dice 係數；只看回覆安全的資料，最高分達門檻才回，同分隨機）→ `replyDelayMs(chatReply)`（`delayMin`～`delayMax` 秒隨機，預設 5～10、各 0～300、最大不小於最小，設定頁 `chatDelayMin`／`chatDelayMax`）後用 `startMacro('reply 文字', 'chat')` 送出（巨集在跑算 `active()`，閒置時也送得出去，停止一切與驗證碼會取消它）。回覆含 `;` 或 `@等待` 的資料一律不送。等待中的回覆記在 `chatTimers`，關掉開關、`stopEverything`（含驗證碼）、`retire` 都會取消；要在閒置時送得出去所以不走 `queueCommand`。

- 限制（`createLimiter`，`take`／`confirm`／`refund`／`noteSent`／`isOwn`；`now` 可注入）：設定多 `cooldownSec`（同一個人的冷卻，預設 60，上限 3600）、`perHour`（全部滾動一小時上限，預設 10）；`take(名字, 文字, 設定)` 依序檢查每小時上限、同一個人的冷卻、同一個人同一句話 `REPEAT_MS`（10 分鐘，比對去標點空白），可以回就預約（同一個人緊接著來的第二句才擋得住）並回票，不行回 null（被拒絕的不占額度）；在 `bestReply` 找到回覆之後才 `take`。送出的那一刻 `confirm`（冷卻與額度改從送出算起），沒送出（被取消、驗證碼辨識中或 `stopReason` 含「驗證」、`startMacro` 回 false）就 `refund` 把額度還回去；等待中的回覆記在 `chatTimers`（計時器 → 票），取消時一併還。送出成功才 `noteSent`，遊戲回印的「你回答…」行由 `createRecorder` 的 `isOwn` 認出（去標點空白後比對、只認一次、`OWN_MS` 5 分鐘內），不記成資料，那個人的來訊也清掉。驗證碼辨識中那一刻的檢查沒有單獨的測試（要模擬整個驗證碼流程）。

- `content.js` 的 `feedChat` 在 `captchaObserver` 的停止關鍵字之後呼叫（閒置時也記），寫 `chrome.storage.local.chatPairs`，寫入排成一條佇列（讀改寫不能交錯）、連不上儲存就當沒記到；記錄一律進行，不受自動回覆的開關影響。測試在 `tests/integration/game/chat-reply.test.js`。
