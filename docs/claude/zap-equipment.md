# 裝備比較

- `zap-equipment.js` 不碰 DOM（解析、屬性正規化與計分、比較、基準存放、穿著清單解析、鑑定追蹤器）。「此物名曰」區塊的欄位標籤中間有空白，不認得的行（文字圖案、`特殊物品非無名裝備…`、`共鑑定…`）一律略過；改解析要用 `tests/fixtures/equipment/` 的真實樣本驗證。
- 比較規則與權重集中在 `zap-equipment.js`（`PRIMARY_GAP`、`PRIMARY_WEIGHT`、`SKILL_WEIGHT`、`RELATED_WEIGHT`、`OTHER_WEIGHT`、`IGNORED_ATTRS`、`ALWAYS_RELATED` 是沒調過時的預設，實際用的是 `normalizeScoreRule(score)` 整理過的規則：設定頁「比較計分」存進 `chrome.storage.local.equipmentScore`＝`{ primaryGap, primaryWeight, skillWeight, relatedWeight, otherWeight, ignored[], related[] }`，數字 0 以上有上限、`primaryGap` 取整數，清單可以是文字或陣列、名稱照 `normalizeAttrName` 整理去重、最多 30 個，存了空清單就是真的沒有，沒存過才用預設；`compareEquipment`／`pickKeepers` 的 `score` 參數，面板 `zap-equipment-ui.js`、商人 `shop-collect.js` 的 `classify`、背包整理 `content.js` 的 `pickKeepers` 三處都要傳，漏傳就退回預設；屬性達門檻的 `keepHit` 也看同一份 `ignored`；沒設定時行為必須和以前完全一樣）、相關屬性別名）：同類別才比、同類別多件時和最弱的比；主要數值相差不到 `PRIMARY_GAP` 只比屬性分數，相差 `PRIMARY_GAP` 以上則把差距乘 `PRIMARY_WEIGHT` 加上屬性分數差，總分大於 0 才算好（主要數值少一點、屬性補得回來也推薦，理由帶「屬性補回」）；屬性分三級權重（`scoreAttrs`）：主要武器的技能（`RELATED_BY_WEAPON`，`skillAttrNames`：劍＝劍術、刀＝刀法、拳套＝拳術是使用者指定的名稱）用 `skillWeight`（預設 3）、`related` 清單（預設 `攻擊`、`輔助氣恢復`、`內功`，對任何人都算相關）用 `relatedWeight`（預設 2）、其餘用 `otherWeight`（預設 1），`ignored` 不計分；同一條屬性兩邊清單都在時用技能的權重；舊的存檔沒有 `skillWeight` 就是預設 3。主要數值（傷害／防禦）的比較不分級。沒有基準可比（類別沒穿、或穿的那件沒讀過）時 `verdict` 是 `none`，只顯示「沒有基準可比」，不是推薦：`pickKeepers` 不留、屬性門檻也不會把它改判 `keep`；商人 `shop-collect.js` 的 `classify` 也一樣不算值得換（`nobase`，只是文字分「身上沒穿這個類別」與「沒讀過穿著」），list 摘要也不建議這類商品。
- 附屬能力門檻（設定頁「附屬能力達到門檻就建議留下」，`chrome.storage.local.equipmentKeep`＝`{ enabled, min }`，預設關閉、門檻 10，`normalizeKeepRule` 在 `zap-equipment.js`，popup.html 因此要載入它）：開著時 `compareEquipment` 在一般比較之後，候選只要有一條計分的屬性（`IGNORED_ATTRS` 以外、正值）達到門檻就改判 `keep`（「屬性達門檻，建議留下」，理由第一句寫哪條屬性達門檻、後面保留原本的理由），還不能穿也算；本來是 `better` 的不改；沒有基準可比（`none`）的不改，維持 `none`（有基準時比現在差或相當才會被門檻改成 `keep`）。同一個鍵的 `equal`（設定頁「和現在穿的相當也建議留下」，預設關、和門檻開關各自獨立）：沒有屬性達門檻、比較結果是 `equal` 時改判 `keep`，文字「相當，建議留下」，`pickKeepers` 會留、商人 `classify` 也算 good（值得換、有「買」按鈕）。`keep` 的 `VERDICT_RANK` 與顏色和 `better` 相同。沒設定時行為必須和以前完全一樣。
- 追蹤器把「你想請…鑑定所有無名物」到「共鑑定…樣無名物」之間的區塊當候選，之外的區塊只用來更新基準（名稱必須是穿著名單內唯一一件）；區塊可能跨封包，所以新增文字先緩衝，靜止 `FLUSH_MS` 後才 `flush`（連續輸出最多延後 `FLUSH_MAX_WAIT_MS`）。開始／結束句也可能被切在兩個封包之間，追蹤器保留上一批最後 40 個字一起比對；結束句一直沒來時超過逾時就關閉這次鑑定，之後的區塊算被動更新。基準依角色分開存（`wornEquipment: { [角色]: Store }`，角色取分頁標題「角色名 - …」），讀取目前穿著用 `mergeBaseline`（沒回應但還在穿的保留舊的、已經沒穿的丟掉），不能整份換掉。
- 鑑定結果在浮層裡依判斷排序（`VERDICT_RANK`：好與屬性達門檻同級、相當、沒基準、差，同級照來的順序，每件插進該級最後面），最多 `RESULT_MAX` 件，超過時移掉最差一級裡最舊的；`blocks` 只依來的順序存，顯示順序每次從 `rank` 重算。
- 「讀取目前穿著」只能走 `startMacro`（`zap-equipment-ui.js` 的 `deps.startSteps`）：先送 `i`，從穿著行（`ˇ` 標記與同一行的 `view #編號`，需要 DOM 節點的 HTML，不是只有文字）拿到編號，再送 `view` 巨集；鑑定每次都不送指令。UI 借用 `zap-panel.js` 回傳的浮層區段與計時；失敗（沒讀到背包、指令被拒、解析不到）都要顯示原因。
- 自動讀取目前穿著（設定頁「主要武器與裝備比較」，`chrome.storage.local.equipAutoRead`＝`{ enabled, commands[] }`，預設關、換裝指令預設 `wear、wield、remove、unwield`，`normalizeAutoRead`／`isEquipCommand` 在 `zap-equipment.js`，清單轉小寫去重、空的退回預設；備份在 helpers 區塊）：只在裝備比較功能開著（`setEnabled`）而且勾了才作用。觸發有兩個：(1) 送出的指令（`content.js` 三個入口：`pumpQueue` 送出佇列、手打的 submit 捕獲、沒有 `@等待` 的遊戲巨集按鍵 `noteManualMacro`，都呼叫 `equipmentUI.noteSent`）任何一段（`;` 分開）的第一個字在清單裡，去抖 3 秒（每次換裝重新計時），換裝成不成功都讀；(2) 遊戲輸出同時出現「【注意事項】」與「這個ＭＵＤ還處於玩家測試期間」（兩段字可能分在不同封包，留最後 300 字比對），之後每次還有輸出就重新等，安靜 5 秒才讀；只重新整理分頁沒有這段輸出就不讀。登入畫面分頁標題還沒有角色名時不送 `i`（還在輸入帳密），等標題有了才讀，2 分鐘還沒登入就放棄。讀取前要 `phase` 是 idle、沒有鑑定進行中、`deps.isBusy()`（`content.js`：巡怪在跑、`macroRuns` 非空、角色忙碌 `charBusy`、驗證碼或真人驗證開著）為 false，不然每 2 秒重看一次，都結束後補讀一次。讀法是差異讀取（`readMode` `diff`，按鈕仍是 `full` 全部重讀）：送 `i` 之後 `diffWorn(基準, 穿著清單)` 依名稱比（同名多件一件配一件），基準裡沒穿了的當場移掉並存檔，只有現在穿著、基準裡沒有的才 `view`（讀完用 `addBaseline` 加進去），都一樣就不送 view；穿著清單解析不到時不動基準。沒變的件保留原本的 `readAt`，所以狀態列「最舊的是幾分鐘前」不會因自動讀取而刷新。不辨認換裝成功或失敗的訊息；遊戲自己展開的別名要使用者加進清單（比對的是送出的字）。
