# 地圖巡怪：巡怪紀錄、手動紀錄、擬人化

- **巡怪紀錄**（`map-hunt.js` 的 `record`／`exportLog`，記憶體裡最多 `LOG_MAX` 行，不寫儲存、不進設定備份）：目標房間、走每一步與走到哪、看房間（怪帶 `<狀態>`、勾選的標 ✓、別人只記人數**絕不記 ID**）、略過原因、開打與結果、只下 fight 每次 `assistJudge` 的判斷、休息（`restStep`：開始休息寫氣與休息線、送休息指令寫指令、回到繼續線寫「休息結束」）、每次看負重（`checkLoad`：讀不到、未超過與下次隔幾間再看、超過後去整理或停止）、停止原因。設定頁「複製巡怪紀錄」送 `HUNT_LOG` 給遊戲分頁（`content.js` 代回 `hunt.exportLog()`），前面加版本號。新增會影響「有沒有走過去、有沒有打」的分支要補一行 `record`。**每輪摘要**（`logRound`，每輪結束、這一輪處理過房間時寫進同一份紀錄（被「重生前停打」提早結束的那一輪，只要送過指令也寫），事件名「輪摘要」，不受 `humanize` 開關影響；掃描不寫）：開始時間離重生整點幾秒、路線（走到的房間序列，最多 `SUMMARY_ROOMS_MAX` 間）、指令清單（連續重複壓成「指令×次數」、`finger` 與 `give` 不帶後面的 ID 與物品、最多 `SUMMARY_TEXT_MAX` 字）、指令間隔最短／平均／最長、看了幾間有怪幾間、和上一輪路線相同或不同。**間隔用指令真正送出的時間算**：`content.js` 的 `pumpQueue` 送完巡怪的項目（單一指令，或巨集拆出來的每一步）就呼叫 `hunt.noteSent`，不是引擎決定要送的時間（排隊等指令間隔，兩者差一個間隔；巨集只決定一次但每一步都有自己的送出時間）。「開始時間離整點幾秒」用這一輪開始時最新量到的伺服器時間偏差（`beginRound` 收 `calibrate` 或等待中重新校準的結果），不是按開始時量的。摘要的組字在模組層的 `summaryLines({ startAt, sends, path, tail })`（`CatworldMapHunt.summaryLines`，`logRound` 與手動紀錄共用，第一行最後接 `tail`）。**手動紀錄**（`content.js` 的 `manualRecord`、`startManual`／`stopManual`，面板「巡怪」列的 `.hmanual`「● 記錄」，開著寫「● 記錄中」、紅底；巡怪列最多六顆按鈕，面板只有 310px，`.hunt-line .mini` 可以換行、靠右，jsdom 算不出排版，這是用真的 Chrome 截圖確認的）：開著時在 document 捕獲階段聽 `submit`，表單是 `#input` 的表單就記下輸入框的值與那一刻的時間（空白不記、聊天照記）；`sendCommand` 送出表單前設 `sendingOwn`，所以擴充功能自己送的（巡怪、觸發、定時、劇本、驗證碼答案、驗證按鈕的 `alias`）都不算。不靠輸出的回聲：遊戲的回聲有時是「> 指令」、有時是單獨一行（使用者貼的真實輸出，巨集送出的兩段也是單獨一行），和一般輸出分不開。**遊戲巨集按鍵也記**（`noteManualMacro`）：`content.js` 本來在視窗捕獲階段聽巨集按鍵（處理 `@等待` 用的，條件和遊戲一樣），沒有 `@等待` 的巨集仍交給遊戲送，只是同時把那一格用 `;` 拆開、每一段記成一個指令，時間都是按下那一刻（遊戲同步全送，樣本裡兩段的回聲也連在一起）；有 `@等待` 的巨集由擴充功能自己跑，owner 是 `PRESSED_MACRO_OWNER`（`pressed`），`pumpQueue` 送出它的每一步時記（真正送出的時間）。空白與 `<enter>` 不記（`noteManualSend` 用 `CatworldTimer.commandText`）。**遊戲的巨集是不是也透過送出表單送出沒有實測**；如果是，submit 那條會重複記一次（目前假設不是：遊戲是直接拆 `;` 送）。房間每 `MANUAL_ROOM_MS`（1 秒）與每記一個指令時看一次 `CatworldMapCollect.currentRoom`，換了才記（起點不算一步）。**分段**：開始時用巨集送一次 `time`（`askGame` 的送出方式換成 `startMacro('time', 'manual')`，閒置時佇列不送；它經過 `sendCommand`，所以不算玩家的）校準伺服器時間偏差，之後按 15 分鐘重生整點（`CatworldMapHunt.RESPAWN_MS`）分段：每記一個指令、每秒看房間、關掉時都先 `rollManual`，伺服器時間跨過這一段的整點就 `writeManualSegment` 寫出這一段（`summaryLines`，三行「手動摘要 第 N 段：…」寫到巡怪紀錄，`hunt.recordLine`，同一份、同一個 600 行上限；N 只算寫出來的段落，沒有指令的段落不寫；「開始時間離整點幾秒」用這一段第一個指令的伺服器時間；第一行最後寫「l 了 N 次」），中間隔了好幾個整點都沒有指令就一次跳到下一個整點。讀不到 `time` 時偏差當 0，第一行前面寫「（伺服器時間沒校準）」。巡怪功能開關關掉時也停止並寫出；只在記憶體裡，不存儲存、不進設定備份。測試 `tests/map-hunt.test.js` 的 `manual:`（`typeIn` 填輸入框再送出表單，和遊戲收到 Enter 一樣會觸發 submit）。**真實遊戲裡按 Enter 是否觸發表單的 submit 沒有實測**（擴充功能自己送指令就是送出表單，遊戲收得到，所以應該是）。設定 `humanize`（預設關，設定頁「擬人化」摺疊）是擬人化功能共用的開關，引擎的隨機都從 `deps.random`（預設平台亂數，測試注入固定值）取。**擬人化的每輪隨機**（`humanize` 為 on 且不是掃描才作用，`humanizeRound` 在每一輪開始時呼叫：按開始、打怪前補掃完、等完重生；關著時 `state.settings` 就是原本的設定物件，行為與以前逐字相同）：①目標順序 `planOrder`：從現在的位置起每次在剩下的目標裡抽一個，權重 1/(步數+1)²（越近越高），排出來的總步數超過「最近的先」的 `ORDER_STEPS_CAP`（1.2）倍就不用、照原本最近的先；`plan` 在 `state.order` 裡挑下一個還在、走得到的目標（有嚴格圖的路線時只在那些裡面挑）。②等長的最短路線：`firstStep` 在「走完全程一樣長」的出口裡隨機挑第一步。③`roundSettings` 每輪換一份設定：重生前停打秒數 ±`JITTER_STOP_RATIO`（30%；設 0＝不停、小於 `JITTER_STOP_MIN_SEC` 的小數字不動，因為取整數會超過 30%）；**只抖動目前補氣模式用的那一條線**，範圍取自 `FIELDS`，±`JITTER_LINE_POINTS`（3 個百分點）：吃藥模式抖吃藥線（原本高於危險線的話抖完仍高於它，不然會先回家、吃不到藥），自己回模式抖休息線（不超過「回到 %」減 1，危險線一定低於它、必要時一起壓低）；重生整點本身不動。`state.settings` 是這一輪用的設定（開著時是 `baseSettings` 抖動過的副本，關著時就是 `baseSettings` 本身，所有讀設定的地方都在呼叫時才取 `state.settings`）。④長停頓 `humanPause`：可以停的點約 `PAUSE_CHANCE`（5%）多停 `PAUSE_MIN_MS`～`PAUSE_MAX_MS`（3～7 秒；**上限一定要小於 `content.js` 的 `NO_REPLY_MS` 8 秒**：撿屍指令送出後遊戲若什麼都不印，看門狗會把停頓當成「疑似需要驗證」而停掉一切），一次抽籤決定停不停與停多久（同一個值縮放成長度，測試才能用固定值測到最長的停頓），只有兩個點：`inspect` 到房間後、判斷房間內容（抵達描述或 `l`）之前，和 `fightRoom` 打完一隻、撿屍指令（`afterKillCommand`）已經送出之後、重數的 `l` 之前；**走路途中絕不停**（移動逾時只有 5 秒，停了會被當成沒走成），撿屍指令也不延後（屍體不能等）。停頓在引擎裡用 `setTimeout` 等（呼叫端 `await` 之後要確認 `state === token`），不動共用的送出佇列，所以其他來源的指令不受影響、指令真正送出的時間（每輪摘要用的）自然包含它（打完一隻後那一次，停頓和撿屍指令排進佇列同時開始，所以撿屍到重數的間隔會比寫的少一個指令間隔），並寫一行「停頓 N 秒（到房間後／打完一隻後）」。只下 fight 模式的「打完一隻後」沒有這個點（那裡由你的觸發規則在打）。幅度都寫死、不開放設定。隨機一律從 `deps.random`（預設呼叫時才取 `Math.random`）取，測試把頁面的 `Math.random` 換成固定值。每輪開始寫一行「擬人化」紀錄（順序與這一輪用的秒數、百分比）。目標順序用的是整張地圖圖示的圖（`state.graph`），學習出口開著時實際路線可能不同，只拿來排順序。⑤**掛機休息**（`humanize` 開著、`loopRounds` 開著、有填 `restReturnCommand`「回到巡怪區的指令／巨集」才作用（欄位在「輪與重生」組，`loopRounds` 開著就顯示，琥珀色的 `advise` 只在擬人化開著時），掃描不休息；沒填就不休息，設定頁的欄位標琥珀色（只在「巡完一輪後等下一個重生」開著時標，關著時本來就不會休息）但**不擋開始**：`FIELDS` 的 `advise`，不是 `required`；`popup.js` 對它也加 `hmissing` 的 class，所以顏色與必填相同，但組標題不加「⚠」也不進 `missingFields`）：`endRound` 每跑完一輪（處理過房間的）由 `countRoundForRest` 數一次（回程指令讀 `baseSettings`，不是每輪抖動的 `state.settings`），數到第一次數完時抽好的 `restEveryMin`～`restEveryMax`（設定頁「擬人化」的「每跑幾輪休息一次」，1～100 的整數、預設 6～12，最多小於最少時拉成最少；讀 `baseSettings`）輪就 `beginRest`：抽跳過 `restSkipMin`～`restSkipMax`（設定頁「一次休息跳過幾輪」，1～20 的整數、預設 1～3，最多小於最少時拉成最少；讀 `baseSettings`）輪、記一行「休息 跳過 N 輪」；**回家指令在待命指令（可能是巨集）跑完之後才送**（`waitTick` 的 `standby` 階段，`state.rest.homed`；和待命指令字串一樣或沒填就不送，待命指令這一輪結束時已經送過），免得巨集的分段指令和回家指令交錯；之後照一般的 `calibrate`，但等的重生整點是「上一輪開始與現在較晚的那個」之後的第一個整點再多跳過 N 個週期（`state.rest`；上一輪跑得比一個週期還久時，只用上一輪開始算會已經過了、休息變成沒休息），算出來的回來時間記一行「休息 約 HH:MM 回來」。到點時 `startRound` 不直接 `beginRound`，走 `returnFromRest`：等氣到 `returnQiLine`（設定頁上看得到的線：吃藥模式是吃藥線 `eatBelow`，自己回模式是休息線 `restBelow`、已經在休息中則要等回到 `restResume`；不能固定等 `restResume`，吃藥模式那個欄位是藏起來的，自己回模式在兩條線之間在家沒人補氣；在家 `vitals` 照常補氣；`RETURN_QI_WAIT_TICKS` 2 分鐘沒到就停止並警報、回程指令不送）→ 送回程指令（可以是任何指令或 `@巨集 N`，`run`、`ride2` 都行，照常展開；要等指令真的送出、巨集跑完）→ 等地圖房間回到巡怪區（`RETURN_WALK_TICKS` 1 分鐘沒回到就停止並警報、不重送；**逾時只算回程巨集跑完之後的 tick**，巨集自己的 `@等待` 不算；指令一直沒送出（被佇列擋住、或 `@巨集` 讀不到而什麼都沒送）另外算 `RETURN_WALK_TICKS`，到了就停止並警報說「沒有送出」）→ 回到後再等 `RETURN_SETTLE_TICKS`（3 秒）讓地圖房間穩定（家在巡怪區的地圖上時送出當下房間還是舊的；從送出指令到這裡是共用的 `walkToArea(token, 指令, 區域, { unsent, missed })`，回花的毫秒數或 null）→ 記「回到巡怪區，回程花了 X 秒」（量到第一次回到巡怪區為止），下一輪的每輪摘要多一行「休息回來：跳過 N 輪，回程花了 X 秒」→ 一般的 `beginRound`，下一次休息要隔幾輪重新抽。面板文字：休息中「休息中，約 HH:MM 回來（跳過 N 輪）」（`describe` 最前面，比補氣的「休息中 X%→Y%」優先；回家指令還沒送時寫「等待指令送完…」）、走回去「休息結束，等氣回到 X%（現在 Y%）」「走回巡怪區…」。停止、驗證碼警報都走 `finish`，進行中的等待在下一個 `await` 醒來時發現巡怪已換而放棄，不會再送任何指令；`phase` 為 `return` 時 `tick` 不動作（`vitals` 照跑）；被「重生前停打」提早結束的那一輪不算跑完的一輪。測試 `tests/map-hunt.test.js` 的 `hunt log:`、`round summary:`、`humanize:`、`humanize pauses:`、`rest:`（待命指令 `home` 把角色送回地圖上、回家指令 `recall` 送到地圖外、回程指令 `back` 送回來；一般的一輪結束把時鐘撥快 16 分鐘讓下一輪馬上開始，決定休息的那一輪不撥）。
- **擬人化的失誤：打錯字與故意走錯路**（`typoPercent` 預設 2、`wrongWayPercent` 預設 1，都是 0～20 的百分比，`humanize` 開著且不是掃描才作用；`typoRoll`、`typoOf`、`askHuman`、`wrongWayPick`、`walk`）：**打錯字**＝把指令最後一個字母重複一次（`ee`、`ll`、`fingerr 某人`，不是方向或常用指令，遊戲回「什麼﹖」），只用在走路（`plan` 送移動前）、`l` 與 `finger`（`askHuman` 取代 `deps.ask`，ID 原樣不動，不然會 finger 到別人或被當成 NPC 學起來）；`fight`／`kill`／吃藥／休息／回家一律不打錯。打錯的先送，`TYPO_DELAY_MS`（1～3 秒）後才送正確的；走路時這段 `phase` 是 `slip`（`tick` 不動作，移動逾時從真正送出才算）。**故意走錯路**＝`plan` 在還有 2 步以上、氣不低於 `WRONG_WAY_MIN_QI`（60%）、這一輪不到 `WRONG_WAY_MAX`（2）次、學習出口關著時，依機率挑一個「在嚴格圖上、不是路線的下一步、不是目標房間、那間有路回來」的出口走進去，`state.detour`（`stage` 為 `out`／`back`、`via`、`home`、`back`）記著，走到那間（`plan` 開頭）馬上走回來，期間不做路過檢查、不看房間；走錯的那一步 `expected` 就是那間，所以不算 `state.wrong`、不會讓目標被略過；位置不對就放棄、照一般流程。計數 `state.slips` 每輪歸零，每輪摘要的第一行多「打錯字 N 次、走錯路 M 次」（擬人化開著才寫）。測試底座的 `REQUIRED` 把兩個機率設 0（舊測試把亂數固定成很小的值，會剛好落在 2% 內），`humanize slips:` 三個測試用 `r: 0.1` 加 20% 驗證。**真實遊戲裡「什麼﹖」之類的回應、故意走進去的房間會遇到什麼，只在 jsdom 驗證過**。
