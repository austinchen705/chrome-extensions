# 解謎查詢（zap 第 4 階段）設計

上層設計：`docs/superpowers/specs/2026-10-19-zap-lookup-design.md`。第 1 階段（打怪）、第 2 階段（無名物品）已完成；第 3 階段（無名裝備比較）使用者決定不做。

## 目的與原因

解謎要在遊戲與 `zap.muds.me` 的步驟頁之間來回切換，而且攻略站有四成以上的步驟只有文字、沒有指令。目標：在遊戲頁面板裡直接看「我現在能解哪些謎」、看步驟、把指令一步一步送進遊戲，並讓使用者邊玩邊補上缺的指令。

## 目標 / 非目標 / 反目標

目標
- 依使用者目前的經驗與內力，把謎分成「條件夠／需自行確認／條件未達」。
- 看步驟、一步一步送出指令、補指令、標記已解過。

非目標
- 不自動連續執行整個謎（一次只送一步）；不判斷謎有沒有真的解成功。
- 不讀技能等級、天賦、背包物品、是否為新手（狀態視窗看不到），這些條件只顯示給使用者自己判斷。
- 不補步驟裡 `run` 路徑的前綴：解謎步驟內的路徑保持網站原樣（可能接在上一步位置後面走）。

反目標
- 把使用者條件不夠的謎標成「條件夠」。讀不到的條件一律歸到「需自行確認」，不猜。
- 一個按鈕送出的指令比使用者看到的多、或在驗證碼出現時還繼續送。

## 資料來源（已查證）

- **總表** `https://zap.muds.me/qu1.htm`：一張表（五欄：名稱、條件、事件相關提示、難度、得到的獎勵），依分類（技能類 9、治裝類 17、道具類 8、寵物類 2、其他類 10）分段；**表裡沒有連結**。
- **步驟頁** `qu*.htm`（共 40 頁，目錄在 `list.html` 的選單，選單項目是「分類 + 名稱 + 連結」，共 47 項）。同一頁可能對應多個謎（例如 `qu1-5.htm` 是玉蕭劍法與彈指神通，`qu1-8.htm` 是葵花神功與自宮）。
- **名稱對不齊**：總表與選單的名稱不一致（「習得凌波微步」/「凌波微步」、「湖底」/「湖底之謎」、「靈鷲宮的委託」/「冰翼無痕」、「神龍教的秘寶」/「神龍教秘寶」）；對應需要正規化比對加一份手動別名表。
- **步驟格式**：多數頁是編號步驟「1.run 2e u;apprentice founder」，一步可含多個以 `;` 分隔的指令；全部約 418 個編號步驟，其中 231 步含指令、187 步只有文字（例如「殺了葉二娘取得小孩」「找到段譽」）。
- **非步驟頁**：有些頁是表格或說明（例如 `qu6-1.htm` 拜師的師父條件表），整頁當文字顯示、不拆步驟。

## 條件解析與分組

總表的條件字串有這些寫法（已全數列舉）：`無`、`N 萬 EXP`（可帶 `[註]`）、`內力 N`（可帶 `[天賦]`）、`內力 ????`、`<技能>相關技能N` / `製藥學技能 N`、`需為新手`、`未知`、`不一定`。

- 可自動比對：經驗（`#exp`）、內力（取**內力上限**，`#max_force`；使用者目前 2022。這是設計者的猜測，需實測確認）。
- 分組規則：
  1. 條件是 `無` → 條件夠。
  2. 可讀的條件都達標，且沒有任何讀不到的部分 → 條件夠。
  3. 可讀的條件達標，但字串另含讀不到的部分（`[天賦]`、技能、`需為新手`、`未知`、`不一定`、`內力 ????`、`[註]` 這類）→ 需自行確認。
  4. 有任何可讀的條件未達 → 條件未達（顯示在最後，仍看得到）。
- 排序：每組內依難度（極易→易→一般→難→極難，`????` 最後）再依總表原順序。
- 讀不到經驗或內力時（狀態視窗被關掉）：所有謎歸「需自行確認」，並提示「讀不到經驗／內力」。

## 使用者補指令與已解過（本機儲存）

- 每個步驟旁有「編輯指令」：使用者填的指令存在 `chrome.storage.local.riddleCommands`，以 `<謎 id>#<步驟序號>` 為鍵，值是指令字串（`;` 分隔）；有填的蓋過網站上的內容，清空就還原。
- 可匯出：「匯出」把 `riddleCommands` 與 `riddleDone` 複製成 JSON 文字到剪貼簿；「匯入」貼上 JSON 還原。
- 每個謎可勾「已解過」，存在 `chrome.storage.local.riddleDone`（謎 id 的集合）；清單有「隱藏已解過」選項（預設隱藏）。
- 資料檔重新產生後，步驟序號可能移動：補的指令以序號為鍵，因此若某謎的步驟數與編輯時不同，該謎的補充指令要標示「步驟已變動，請確認」，不能悄悄套用到錯的步驟上。（建構者決定如何記錄「編輯當時的步驟數」。）

## 送出指令

- 每個步驟有「送出」按鈕，一次把該步驟的指令（以 `;` 分隔；`<span>` 之類標記要先清掉）依序送進遊戲，走現有的共用送出佇列與指令間隔，不另開通道。
- 送出中算 `active()`（同巨集 `macroRuns`）：驗證碼偵測、看門狗要作用，出現驗證碼時要停止並作廢尚未送出的指令；`stopEverything` 要能取消；一個步驟要等最後一個指令真的送出才算結束（見專案 `CLAUDE.md` 的「遊戲巨集的 @等待」一節對 `macroRuns` 的處理）。
- 該步驟沒有任何指令時，「送出」鈕停用。
- 不自動接著送下一步；送完不標記步驟完成（使用者自己判斷）。

## 顯示

- 面板新增「解謎」列與按鈕；展開後在面板內顯示清單與步驟（shadow DOM、不開新分頁；樣式與第 1 階段的怪物清單一致）。
- 清單：三組（條件夠／需自行確認／條件未達），每個謎一行：名稱、難度、條件、事件提示、獎勵；有搜尋框（名稱、提示、獎勵）。
- 點一個謎進入步驟檢視：每步顯示序號、原文（文字與指令）、「編輯指令」、「送出」；可返回清單。
- 步驟原文照網站顯示，指令部分用等寬字體標示；使用者補的指令顯示成「已補」。

## 資料與程式組織

- 併入 `tools/gen-zap-data.js` 與 `zap-data.json`，新增 `riddles` 欄位（不另開資料檔）；`zap-data.json` 仍由 background 懶載入，新增訊息 `ZAP_RIDDLES`（回傳整份清單與步驟）。
- 資料結構（建議，建構者可調整）：`{ id, category, name, condition, hint, difficulty, reward, page?, steps?: { no, text, commands }[], pageText? }`；`commands` 是從步驟文字抽出的指令字串（可能為空）。
- 新增不碰 DOM 的模組（例如 `zap-riddles.js`）負責條件解析、分組、指令切割；與其他 `zap-*` 模組一樣要同時加進 manifest、popup.html（若 popup 用得到）與 popup 備援注入 `files`，且在 `zap-panel.js` 之前。
- 產生腳本在解析失敗（總表解析出的謎少於 40 個、或步驟頁抓不到）時要失敗、不覆寫資料檔；找不到步驟頁的總表項目與找不到總表項目的選單項目要列在報告裡。
- 手動別名表與步驟指令的補充：沿用 `tools/zap-overrides.json` 的做法（建構者定格式），用來修正名稱對應；使用者在面板補的指令不進這個檔，只存本機。

## 留給建構者決定

- 步驟頁的解析方式（編號步驟的辨識、一步含多個指令的切割、非步驟頁的判斷）與「指令」和「說明文字」的區分（同一步可能前半是指令、後半是說明，例如「1.run e n eu;ask yueh about 令狐沖」與「發呆看洪七公表演…」）。
- 名稱對應的正規化規則與別名表。
- 面板內清單與步驟檢視的版面、與怪物清單／浮層並存時的排版。
- 補指令的「步驟已變動」偵測方式。
- 測試 fixture：存縮減過的 `qu1.htm` 與若干步驟頁；測試不連網。
- 依專案 `CLAUDE.md`：升 `manifest.json` 版本、`CHANGELOG.md`、README、`CLAUDE.md` 現況。

## 已知限制

- 條件只能比對經驗與內力；技能、天賦、物品、新手身分要使用者自己判斷。
- 「內力」用內力上限比對是猜測，需要實測校準；若不對要調整。
- 約四成步驟只有文字，需要使用者逐步補指令；補的指令只存在本機瀏覽器。
- 攻略站的內容可能有誤或過時；一步送出的指令是否正確由使用者負責確認。
